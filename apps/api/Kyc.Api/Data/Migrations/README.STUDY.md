# Study: `Data/Migrations`

Study tour of this folder. Distinct from the official README. Parent: [../README.STUDY.md](../README.STUDY.md).

**Aligned with:** `main` after `AddCaseReviewComment`.

## Purpose

Migrations are **versioned schema**, the same idea as Prisma `migrations/` SQL files. They are how every environment (laptop, CI Postgres, future prod) reaches the same tables.

This folder is generated by `dotnet ef migrations add`. You **read** `Up`/`Down` in code review; you do not treat Designer files as literature.

## Why so many files per change

Each migration is a **pair** plus a shared snapshot:

| File | What it is | Read it? |
|---|---|---|
| `YYYYMMDDHHMMSS_Name.cs` | `Up()` / `Down()` — the actual DDL intent | **Yes.** This is the review artifact. |
| `*_Name.Designer.cs` | Snapshot of the model at that migration | **No** (noise). |
| `AppDbContextModelSnapshot.cs` | Current full model EF diffs against next time you add a migration | **No**, except when diagnosing a drift bug. |

History on `main` (order matters):

| Migration | Why it exists |
|---|---|
| `InitialCreate` | Empty-host proof (KYC-004). Schema pipeline works. |
| `AddTenant` | `tenants` |
| `AddUser` | `users` + unique (TenantId, Email) |
| `AddCase` | `cases` + FormData |
| `AddCaseReviewComment` | `ReviewComment` on cases (KYC-035) |

**KYC-014 (tenant filters) added no migration.** Filters are C# in `AppDbContext`, not columns. If someone says “isolation is a migration,” correct them.

## Angular analog

Prisma: you change `schema.prisma`, run `migrate dev`, commit the SQL. Here: you change entity + `*Configuration`, run `dotnet ef migrations add NameOfChange --output-dir Data/Migrations` from `Kyc.Api`, commit the three files, apply with `dotnet ef database update`.

[EF migrations](https://learn.microsoft.com/ef/core/managing-schemas/migrations/)

Commands (runbook, not duplicated): [apps/api/README.md](../../../../README.md).

## How to read a migration in 2 minutes

Open the non-Designer `.cs`. Example `AddCaseReviewComment`:

- `Up`: `AddColumn` ReviewComment, varchar(2000), nullable.
- `Down`: `DropColumn` — rollback story.

Ask: does this match `CaseConfiguration` and the entity? If `Up` adds a column the configuration forgot, the next `migrations add` will try to add it again.

## How this folder touches runtime

**Not on the request path.** Applying migrations is an ops/dev step (`database update` or `MigrateAsync` in Postgres tests). The running API does **not** auto-migrate on `dotnet run` (good: app start ≠ schema change).

CI (`PostgresApiFactory`) calls `MigrateAsync()` when `KYC_TEST_POSTGRES` is set so jsonb tests run against the real history, not `EnsureCreated`.

## Today vs target

More migrations will appear for documents and audit. Never rewrite old migrations that already ran elsewhere; add a new one. Same rule as Prisma in production.

## What to skip

- Every `*.Designer.cs`
- `AppDbContextModelSnapshot.cs` unless `dotnet ef migrations add` produces an unexpected no-op or huge diff
- Hand-editing applied migrations
